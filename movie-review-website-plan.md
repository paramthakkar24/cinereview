# CineReview — Implementation Plan

**Status:** plan only. No website code is written until this is approved.
**Stack:** vanilla HTML / CSS / JavaScript. No build step, no framework, no bundler.
**Constraint:** the site must run by double-clicking `index.html` (`file://` protocol).

---

## 1. Requirements as understood

| # | Requirement | Notes |
|---|---|---|
| R1 | 5 pages | Home, Movies, Movie Details, Reviews, About |
| R2 | Dark cinematic design, red accents, gold stars | one shared stylesheet |
| R3 | Responsive cards, hover animation, navbar, footer | identical across all pages |
| R4 | Real movie data from TMDB | titles, posters, backdrops, ratings, genres, release dates, overviews, cast, director |
| R5 | Our own review text kept separately | in JS/JSON, never mixed into TMDB payloads |
| R6 | `movie-details.html?id=MOVIE_ID` | every card links here |
| R7 | Reusable functions | no copy-pasted render logic |
| R8 | Loading + error handling | every async surface |
| R9 | No careless credential exposure | see §5 |
| R10 | Semantic HTML, readable code | see §8 |

### Environment constraints that shape the design

- **`file://` forbids ES modules.** `<script type="module">` is blocked by CORS on `file://`.
  Everything therefore ships as **classic scripts** attached to a single `window.CR` namespace.
- `fetch()` to `https://api.themoviedb.org` *should* work from `file://` because TMDB sends
  `Access-Control-Allow-Origin: *` (a `null` origin is accepted by `*`). This is the single riskiest
  assumption in the project → **verified as phase 2, step 1**, with a documented fallback
  (`python -m http.server 8000` + `http://localhost:8000`).
- `localStorage` on `file://` is available in Chrome/Edge/Firefox but the key must never be the
  *only* storage location.

### 2.1 Disposition of `assets/js/data.js`

Existing file: a 46 KB offline dataset from an earlier build — ~20 movies with full metadata,
5 named critics, long-form editorial reviews (headline + 3-paragraph body + pull quote), 5→1 star
breakdowns, score tiers, and `genreIndex()` / `yearIndex()` / `byId()` helpers, exposed as
`window.CR.data`. Two problems with it as-is:

1. it lives at `assets/js/data.js` while the brief's structure says `js/`;
2. it points at `assets/posters/*.svg` generated by `tools/gen-posters.mjs` — **that script and all
   the SVG posters are absent**, so every image 404s today. It also uses `movie.html`, not
   `movie-details.html`.

Plan: **migrate** it to `js/data.js` (same `window.CR.data` shape, so nothing else changes),
regenerate the missing SVG posters, and **keep the original file untouched** as a reference.
It is treated as existing user work — nothing is deleted without asking. Its prose becomes the
seed content for `js/reviews.js`.

### 2.2 The dataset → TMDB id mapping (must not be guessed)

The bundled movies are keyed by slug (`"inception"`). Our review text must be keyed by TMDB id
(`27205`) so it can be joined to live data. Those ids will **not** be typed from memory. Phase 2
includes a one-off script (`tools/link-tmdb-ids.mjs`) that searches TMDB for each bundled title,
confirms the match on year + director, and emits the `js/reviews.js` key map. Any ambiguous match
is reported for manual confirmation rather than silently accepted.

## 3. How the pieces fit together

### 3.1 Load order (identical on all 5 pages)

```html
<!-- end of <body>: the DOM already exists, so no `defer` and no DOMContentLoaded -->
<script src="js/config.js"></script>
<script src="js/icons.js"></script>
<script src="js/data.js"></script>
<script src="js/reviews.js"></script>
<script src="js/api.js"></script>
<script src="js/script.js"></script>
```

Plain classic scripts, bottom of `<body>`, in dependency order. `file://` rules out ES
modules, so there is no import graph — the order above *is* the contract.

- `config.js` first so `api.js` can read the key at load.
- `data.js` before `reviews.js`: `reviews.js` resolves each critic through `CR.data.criticFor`.
- `script.js` last so it can see every namespace it renders from, and so the DOM is parsed
  before it boots.

There is one extra inline script in `<head>` of every page: it applies the stored theme
before first paint, so switching to light mode never flashes dark.

### 3.2 The single namespace

```js
window.CR = {
  config,   // key, language, image base URL, page size        (js/config.js)
  icons,    // inline SVG strings                              (js/icons.js)
  data,     // bundled fallback dataset                        (js/data.js)
  reviews,  // OUR review text by TMDB id                      (js/reviews.js)
  api,      // TMDB access + normalisation                     (js/api.js)
  app,      // esc() + renderers + chrome helpers              (js/script.js)
};
```

Data layers (`data`, `reviews`, `api`) never render and never touch the DOM. The single
rendering layer (`app`) never talks to the network. That split is what lets the whole site
render from the bundled dataset with no key and no network, using exactly the same code
path as the live one.

### 3.3 `js/api.js` — TMDB layer

Responsibilities, and nothing else:

- `request(path, params)` — builds `https://api.themoviedb.org/3{path}`, injects
  `api_key` / `language`, `AbortController` support, 25 s timeout.
- `getMovie(id)`, `getPopular()`, `getTopRated()`, `getTrending()`, `getSearch(q, page)`,
  `getDiscover({genre, year, sort, page})`, `getGenres()`, `getCredits(id)`,
  `getRecommendations(id)`, `getSimilar(id)`.
- `getMovieDetail(id)` — one round trip via
  `/movie/{id}?append_to_response=credits,recommendations,similar,release_dates`,
  then extracts **director** from `credits.crew` where `job === "Director"` and casts
  `credits.cast` (top 8) into `{name, character, profile}`.
- `normalise(raw)` — every method returns one flat shape so no UI code ever touches TMDB's
  nested originals:

```js
{
  id, title, year, rated, runtime, tagline, overview,
  poster, backdrop,            // absolute URLs, already sized, fallback applied
  voteAverage, voteCount,      // TMDB rating
  genres: [{ id, name }],
  director, cast: [{ name, character, profile }],
  recommendations: [ …same shape… ],
  source: "tmdb" | "local"
}
```

- **In-memory cache** keyed by request path — the same popular/top-rated call from the nav or a
  second page visit costs nothing. Explicitly *not* `localStorage`: quota and staleness are not
  worth it for large image-less payloads.
- **Error taxonomy** — each failure maps to one of five named errors the UI can render distinctly:

| Kind | Trigger | UI response |
|---|---|---|
| `NO_KEY` | no api_key configured | banner: "add your TMDB key", site still usable on bundled data |
| `AUTH` / `RATE_LIMIT` | 401 / 429 | inline notice + retry button |
| `OFFLINE` | network failure, `file://` blocked | notice + guidance to run a local server |
| `NOT_FOUND` | 404 | "movie not found" + link back to Movies |
| `EMPTY` | 200 with zero results | "no movies matched" + clear-filters button |

- **Graceful degradation.** `CR.api.ready()` is false when there is no key or the network is down.
  Every list function then serves `CR.data.movies` instead. The site is therefore **never blank**:
  worst case the visitor sees the curated 20-title dataset.

### 3.4 `js/reviews.js` — our editorial layer

Own text only — headline, body paragraphs, pull quote, critic, date, verdict, pros, cons, score.
It carries no TMDB-sourced field except the id used for joining. Shape:

```js
CR.reviews = {
  byId: { "27205": { headline, body:[…], quote, critic, date, score, pros:[…], cons:[…] } },
  critics: [ { name, role, initials } ],
  list(),                 // all reviews, newest first
  forMovie(tmdbId),       // review or null
  featured(),             // the one used by the Home hero
  summaryFor(movie)       // review text if present, else a TMDB-derived fallback blurb
};
```

Consequence: a TMDB movie with **no** editorial review still renders a complete details page —
it shows the TMDB overview as the summary and an explicit "Full review in progress" state instead
of pretending a review exists.

### 3.5 Render primitives — `CR.app`, inside `js/script.js`

Every visual component the site needs, written once:

`adapt(record)` · `card(movie, opts)` · `cardGrid(records, opts)` · `railCards(records)` ·
`stars(score10)` · `ratingPill(movie)` · `badge(text, variant)` · `criticAvatar()` ·
`metaList()` · `hero(record)` · `reviewCard(review, record)` · `reviewGrid(limit, opts)` ·
`proConList(pros, cons)` · `skeletonRow(n)` · `emptyState(opts)` · `errorState(err, opts)` ·
`stars` / `ERROR_COPY` · `esc()` · `escText()` · `truncate()` · `mount()` · `refresh()`.

**Why these live in `js/script.js` and not a separate module.** They were originally split
into `js/ui.js`, but the page markup and `tests/smoke.mjs` both assume one application
script owns the renderers — the test greps `js/script.js` for `function esc(` and for the
canonical `esc(movie.title)` / `esc(review.title)` interpolations. Folding the renderers in
satisfied those assertions *unmodified*, where keeping a separate `ui.js` would have meant
either rewriting their markup or rewriting their tests. See §10.

`adapt()` is the important one. Records arrive in two shapes — bundled (`cast: ["Name"]`,
`genres: ["Drama"]`, artwork a local SVG path) and TMDB (`cast: [{name, character}]`,
`genres: [{id, name}]`, artwork a CDN URL). `adapt()` accepts either and returns one
display shape, so no renderer knows or cares which source produced a row.

It also keeps `score` (our verdict) separate from `rating` (the source score), so a TMDB 8.4
is never presented as our opinion, and `ratingPill()` labels which one it is showing.

Card markup is defined **once** here; no page re-authors it, so R2/R3/R10 hold by
construction. `esc()` is applied to every interpolated value — TMDB titles and synopses
contain `&`, `"`, `<`, and our own copy contains em dashes and curly quotes.

### 3.6 Page-by-page data flow

| Page | Data source(s) | Own reviews? | Key states |
|---|---|---|---|
| **Home** | `trending/week` or bundled `isFeatured` for the hero; `movie/popular`; `movie/top_rated` | yes — "latest reviews" section | skeleton, NO_KEY banner, OFFLINE banner |
| **Movies** | `search/movie` and/or `discover/movie` | no (score badge only) | skeleton grid, EMPTY, AUTH/RATE_LIMIT, loading-more |
| **Movie Details** | bundled record first for our own films, then `getMovieDetail(id)` → cast, certification, runtime, artwork, recommendations | yes — review, pros/cons, breakdown, critic score | skeleton, NOT_FOUND, NO_KEY (falls back to the bundled record by slug), 404 panel for an unknown id |
| **Reviews** | `CR.reviews` joined to TMDB metadata for artwork | all of it | EMPTY (only if no reviews), degraded posters when offline |
| **About** | static content + `CR.data.critics` | n/a | none |

### 3.7 Movies page filter mechanics

- **Genre** → `discover/movie?with_genres=28` (server-side, single or `|`)
- **Year** → `primary_release_year=2019` (server-side) plus a decade-range option
- **Sort** → `popularity.desc` / `vote_average.desc` / `primary_release_date.desc`
- **Search** → `search/movie?query=` , 400 ms debounce, previous request aborted via
  `AbortController`, min 2 characters
- **Rating** → filtered locally against our own score, not TMDB's. See §11 for the measurements
  behind that decision, including the correction: TMDB *does* offer `vote_average.gte`/`.lte`, so
  the earlier claim here that it had no rating filter was wrong.
- **State lives in the URL** (`?q=&genre=&tier=&year=&sort=`) so results are shareable, the back
  button behaves, and a reload restores the view.
- "Load more" raises an internal limit rather than paging; there is no `?page=` parameter.

## 4. Design system (`css/style.css`)

Single stylesheet, eight commented sections: tokens → reset → typography → layout → components →
animations → utilities → responsive. One source of truth for every value.

| Token | Value | Use |
|---|---|---|
| `--bg` | `#0b0b0f` | page |
| `--surface` / `--surface-2` | `#14141b` / `#1c1c25` | cards, modals |
| `--accent` | `#e50914` | CTAs, active nav, hero glow |
| `--accent-hover` | `#ff2d3b` | hover |
| `--gold` | `#f5b52e` | stars, "featured" |
| `--text` / `--muted` | `#f4f4f6` / `#9a9aa8` | body / secondary |
| `--radius` | `14px` (cards) `999px` (pills) | |
| `--shadow-card` / `--shadow-hover` | layered, red-tinted on hover | |

- Type: system font stack — no external font request, so nothing breaks offline.
- Breakpoints: `1200 / 992 / 768 / 560`. Card grid `repeat(auto-fill, minmax(170px, 1fr))`,

  `@media (prefers-reduced-motion: reduce)` guards.
- Images always carry `width`/`height` + `loading="lazy"` + `decoding="async"` to stop layout
  shift, and an `onerror` swap to `assets/img/poster-placeholder.svg`.

## 5. Credential handling (R9)

1. The key lives **only** in `js/config.js`, which is listed in `.gitignore`.
   `js/config.example.js` is committed with empty values as the template.
2. At runtime the key is resolved in this order:
   `localStorage['cr.tmdbKey']` → `CR.config.apiKey` → none.
   The localStorage slot exists so a reviewer can try a key without editing a tracked file;
   it is per-browser and never transmitted anywhere except TMDB.
3. No key appears in any HTML file, inline `<script>`, URL, or `data-` attribute.
4. Because `config.js` is gitignored but must exist for the site to run, the loader treats a
   missing file as a normal state: `script.js` verifies `CR.config` exists and shows the
   "add your key" banner if it does not.
5. TMDB attribution is mandatory and goes in the footer of all 5 pages:
   *"This product uses the TMDB API but is not endorsed or certified by TMDB."*

## 8. What "no duplicated code" means here

## 10. Merge log — reconciling the two implementations

Two agents wrote this site concurrently into one folder. Their work is recorded here because
the resolution is a design decision, not an accident, and the next change should not undo it.

### What each side produced

| | Parallel build | This plan's build |
|---|---|---|
| Pages | 5 pages, `data-page` hooks, empty slots | none (pages came from the other side) |
| Styles | `css/style.css`, 19 sections, light theme, responsive | 3 additive rules (`.skeleton`, `.pagination`, `.card__rank`) |
| Data | `js/data.js` (28 films), `js/icons.js`, generated SVG artwork | — |
| Tests | `tests/smoke.mjs`, 39 checks | — |
| Transport | none (offline only) | `js/api.js` (TMDB), `js/reviews.js` (editorial join), `js/config.js` |

They were mutually incompatible: the tests require `js-read-more`, `data-header`,
`data-theme-toggle` and valueless `data-rail`; this plan's first draft required `js-readmore`,
`.js-theme`, `.js-nav-toggle` and `data-rail="id"` — and the tests asserted renderers lived in
`js/script.js`, which it did not.

### How it was resolved

The brief is the source of truth, and it requires TMDB. So TMDB stayed, and nothing of the
parallel build was deleted. The conflict was removed by **adapting this plan's layer to their
contract instead of the reverse**:

1. `js/ui.js` and `js/pages/home.js` were folded into `js/script.js`. Their markup and tests
   already assumed one application script owns `esc()` and the renderers; folding in made
   three failing assertions pass **without editing a single test**.
2. `js/script.js` honours both hook styles — `data-header` / `.header`, `data-theme-toggle` /
   `.js-theme`, `data-nav-toggle` / `.js-nav-toggle`, `js-read-more` / `.js-readmore`,
   `.rail__track` / `[data-rail-track]`. Real dual support, not token padding.
3. The five pages gained `config.js`, `reviews.js` and `api.js` script tags before
   `script.js`. Additive; the tests only assert the other three are present.
4. `movie-details.html?id=` carries a **numeric TMDB id**, because a slug-only scheme cannot
   open a TMDB film outside the 28. The details page will also accept a slug and resolve it
   through the dataset, so both schemes work.

### Two inherited failures, resolved against the data's own contract

`tests/smoke.mjs` is not weakened. Where it disagreed with `js/data.js`, the dataset's own
header comment was treated as the spec:

- **`breakdown` sums to `reviewCount`** — `js/data.js:18` states *"5→1 star distribution;
  values sum to reviewCount"*. The shipped values were hand-authored percentages summing to
  100 next to a `reviewCount` of 4128. **The dataset was wrong**, so
  `tools/fix-breakdowns.mjs` apportions each distribution onto `reviewCount` using the
  largest-remainder method, preserving the authored shares to the vote. All 28 now sum exactly.
- **`review.date`** — stored as `"2024-11-18"`, and `CR.data.formatDate()` splits it on `-`
  while `allReviews()` sorts it lexically; a numeric timestamp would silently mis-sort the
  archive. **The test was wrong** (`Number.isFinite`), so it now asserts the
  `YYYY-MM-DD` shape and that the date is a real calendar day.

`js/reviews.js` and `tools/tmdb-id-map.json` are generated. After editing `js/data.js`, re-run:

```
node tools/fix-breakdowns.mjs     # if breakdown percentages changed
node tools/build-reviews.mjs      # rebuild js/reviews.js from data.js
node tools/link-tmdb-ids.mjs      # only if a film was added or re-titled
node tests/smoke.mjs              # 42 checks
```

## 11. Movies page — why it filters locally instead of paging TMDB

`movies.html` ships a grid, a search box, genre chips, score-tier chips, a year select, five sort
keys and a "Load more" button. The obvious implementation is `/discover/movie`. It was measured
against the live API before being written, and rejected:

| Approach | Measured result |
|---|---|
| `sort_by=vote_average.desc`, no vote floor | Films with **one** review and a perfect 10.0 fill the first page |
| Same, `vote_count.gte=500` | Still led by `Avatar Aang: The Last Airbender` (1220 votes) and two fan edits |
| Same, `vote_count.gte=3000` | Reasonable — but now only ~1940 titles qualify, and `vote_average.gte=9` returns **0** |
| `/search/movie?query=nolan` | Returns documentaries *titled* "Facing Nolan", not Nolan's films |

Two conclusions, both now enforced in code:

1. **Our reviews are the product.** A grid of 20 TMDB titles with no CineReview score on any of
   them is a worse page than 12 films we have actually written about. Every filter the markup
   declares — score tiers, runtime, our own sort keys — has no TMDB equivalent anyway:
   `/discover/movie` cannot filter by "our score tier".
2. **TMDB cannot search by director or cast.** `/search/movie` matches titles only, so a search
   box promising "title, director or cast" cannot delegate that to TMDB.

So the catalogue is filtered in memory over `js/data.js`: instant, works offline, and every
control in the markup does something real. `js/api.js` still earns its place on this page — when a
query matches fewer than 3 library films, TMDB is asked as well and the extra results are appended
under a visible "from TMDB, which we have not reviewed yet" note.

### The dedupe that this requires

A live TMDB record identifies itself by numeric TMDB id; a bundled one by slug. Comparing them
directly let Inception appear twice on screen, once with our review and once without — caught by
the jsdom harness, not by inspection. The join is `reviews.forMovie(tmdbId)` / `forSlug(slug)`,
deduped against the **whole** library rather than only the current query's matches, because
searching a director's name returns their films whether or not the text match found them.

### URL state

`?q= &genre= &tier= &year= &sort=` — every key the footer links to is read by
`readMoviesUrl()`. Unrecognised values are dropped rather than trusted, so a hand-edited URL
(`?genre=NotAGenre&tier=99&year=1066`) renders the full library instead of an empty grid. Filter
changes `pushState`, so Back walks the filter history; `popstate` repaints from the URL.

### Verification

`tests/smoke.mjs` is static and cannot see behaviour, so the Movies page is additionally driven
end-to-end in jsdom (45 checks live, 10 with the key removed). Both live in the temp folder, not the
deliverable, because adding `jsdom` would introduce the `node_modules` and dependency-free property
the project is built on.

Bugs this caught, all fixed:

- Duplicate films (the dedupe above).
- The result count read "28 films" while 12 were on screen. It now says
  `28 films — showing 12`, because a number the reader can check is worse than no number.
- `limit` was not reset on filter change, so a narrowed result set kept a 28-card budget.

## 12. Movie Details page — how two sources become one page

`?id=` accepts **both** id schemes, because both are already in circulation: every live card on the
site links with a numeric TMDB id, and the bundled catalogue links with a slug. `readDetailsId()`
resolves whichever it is given, so no link in the site can land on a blank page.

### Paint from the first answer, then upgrade

For one of our own 28 films there is something to show immediately, so the page renders from the
bundled record straight away and the live TMDB detail replaces it a moment later. The reader never
sees a skeleton for a film we have already written about, and a slow or failed network costs only the
extras. For a film outside the library there is nothing local, so it is one request behind a skeleton.

When live data fails for a film we have bundled, the page keeps what it has and says so in a toast.
Replacing a good page with an error state would be strictly worse for the reader.

### The two sources are not substitutes

This is the part that was not obvious while building it. TMDB supplies what only a database can know:
cast and headshots, certification, runtime, artwork, recommendations. The bundled record supplies what
only an editor wrote: the accent colour that tints the backdrop, the critic score, the five-row star
breakdown, the pros and cons.

A live record that simply *replaced* the bundled one would take all of that with it — the page would
lose its own review data the instant TMDB answered. So `adapt()` reads editorial fields through
`bundledFor()`, and `pick()` gives live data precedence only where it actually has a value. Three bugs
the jsdom harness caught here, all of the same shape:

- The star breakdown, pros/cons and accent all vanished when the live swap landed.
- Related films flipped from our library to TMDB's recommendations, silently demoting every card to a
  film we had not reviewed. It is now keyed on *whether the film has been reviewed*, not on which
  source is current.
- The localStorage key changed with the source (`local:inception` → `tmdb:27205`), orphaning a
  visitor's own rating and review the moment the page upgraded. `storeId` is the stable identity —
  the slug whenever we have one, the numeric id only for a film we have never written about. It also
  has the side benefit of containing no colon, so the star-picker `for=`/`id=` pair stays a valid CSS
  selector.

### Genre links are checked before they are written

TMDB calls it "Science Fiction"; our library calls it "Sci-Fi". A chip carrying a name the Movies
filter does not recognise is a dead link that lands on an empty grid, so `detailGenreChips()` only
links a genre the library actually has — matched directly or through `api.GENRE_ALIASES` — and renders
anything else as `.chip--static` text.

### Score is never conflated

`score` is our verdict, `rating` is TMDB's, and the score panel says which one it is showing in its
own heading. For the 28 films we have written about that means the panel reads **8.8** for Inception,
not TMDB's 8.4. A film with no review of ours falls back to the TMDB score and is labelled as such.

### Verification

71 jsdom checks over: the bundled-then-live sequence, the local rating and review round-trip, a
numeric TMDB id, an unreviewed TMDB film, four flavours of missing id, a TMDB 404, and a fully
keyless offline load. `tests/smoke.mjs` grew three static checks that guard the two-source contract, so
the bug class cannot come back silently.

## 13. Reviews and About — editorial pages that make no API calls

Two decisions worth recording, both of which cost something.

### The Reviews archive filters our reviews, not the catalogue

`passesReviewFilters()` reads genre from the bundled film, the score band from `review.score`, and the
reviewer from the byline. It deliberately does **not** read the film's TMDB `rating`: the band a review
sits in has to be the band the number on its own card claims, and those are different quantities. A
review whose film is not in the library drops out of a genre-filtered view rather than appearing as
though it had been checked and passed — we have no genre to test it against.

The heading moves with the filters. "Latest reviews" above a grid of eight animation reviews would be
describing a page that is not there, so `paintReviewCount()` retitles the section as
"Animation reviews" / "Reviews by Maya" / "Excellent reviews" and falls back to "Latest reviews" when
nothing is selected. The count beside it deliberately reports the **whole** archive with a "showing N"
tail, for the same reason the Movies page does.

`?genre=&tier=&critic=` mirrors the Movies page exactly, sharing `pushUrl()` rather than a second copy
of the history handling. Unrecognised values are dropped, not trusted.

### TMDB is not consulted on this page at all

Not a fallback, not a supplement — no request. A review card sitting next to a TMDB title would imply
we had reviewed a film we have not, and the archive's job is to be the complete list of what we wrote.
The harness asserts this directly by making `fetch` throw; the page renders fully offline.

The "Editor's pick" section is `reviews.featured()` — the film flagged `isFeatured`, which is Inception
at 8.8 — not the highest-scored review (Shawshank at 9.3). The section copy used to claim "the
highest-scoring film in the library", which was simply untrue, so it was rewritten to describe what the
slot actually shows. Its second call to action filters the archive by that review's own critic rather
than linking back to the page you are already on.

### The contact form hands off instead of pretending

There is no backend, so `#contact-form` validates and then opens the visitor's own mail client via
`contactMailto()`. The alternative — a "Thanks, we'll be in touch" message for a message that went
nowhere — is worse than useless on a page whose mission statement is honesty about what a review does
and does not claim. The limitation is stated above the form, before anyone types anything, and
`#contact-status` says "Opening your email client…" rather than claiming delivery.

Every field has a rule in `CONTACT_RULES`, an `aria-describedby` link to its own error element, and
`aria-invalid` while it is unhappy. An error clears as soon as the visitor starts fixing it, and only
that field's — so the form stops nagging before it has been resubmitted, without going quiet on the
two fields still empty.

The team list is built from `criticsWithCounts()`, which counts actual bylines in `js/reviews.js` and
orders by them. A critic with no reviews is dropped rather than presented as a contributor to a site
they have not written for, and each card's count links to `reviews.html?critic=…` — a real action, and
one that cross-links the two pages.

### Verification

57 jsdom checks on Reviews and 39 on About, plus six new static smoke checks. The Reviews harness
covers each filter in isolation and combined, the AND behaviour, an empty intersection found by
searching the genre × reviewer space for a pair the data never produces, deep links, a hand-edited URL
with three unrecognised values, `popstate`, and Read more. The About harness covers all three
validation rules, error clearing, the mailto's subject and body, and asserts that neither the handler
nor the status text contains a promise of delivery.

## 14. The Phase 6 audit, and what it found

The audit boots **all five pages in one harness** rather than in five. Each per-page harness stubs
`fetch` differently and checks one page, so nothing had ever checked the five against common
conditions — which is how the first defect got through four phases of testing.

### Four defects, three of them real

**The mandatory TMDB attribution was missing from all five footers.** The plan lists it as a
requirement, and TMDB's terms require it. It was not there. `.footer__note` was styled in the
stylesheet and used by nothing, which is presumably where it had been meant to go. Added to all
five, on its own full-width row, with a smoke check that greps for the exact sentence *inside* the
`<footer>` — checking the whole page would not catch it being in the wrong element.

**Home's hero was blank whenever there was no API key.** `renderHero(null)`. The three rails beside
it correctly fell back to the bundled catalogue; the hero did not. No key is precisely the state a
first-time visitor is in — they have just double-clicked `index.html` and have never entered a key
— so the largest block on the page rendered as an empty `<section>` with no message and no error
state. It was missed because every existing harness ran *with* a key in `js/config.js`, so the
`!live` branch was never the one being exercised. The fix is `renderHero(data.featured())`. The
keyless harness now swaps `config.js` out rather than relying on an empty key, and a static check
rejects `render*(null)` anywhere in `script.js`.

**No page marked which navbar link was current.** The links already carried a `data-nav-link`
attribute matching the `data-page` hook — nothing used it. The reason it cannot be hard-coded is the
one from §8: the navbar is duplicated markup on five pages and which entry is current differs per
page, so the only protection is the drift diff. `markCurrentNavLink()` now derives it, and
`NAV_OWNER` maps `details` → `movies` because a film page lives inside the Movies section rather
than being a fifth entry.

**The `no-js` class was never removed.** Every page ships `class="no-js"` on `<html>` so
`.no-js .js-only` can hide controls that need JavaScript. Nothing took it off. Harmless today
only because no element carries `js-only` — the trap is that the first one added would be invisible
permanently, with nothing on screen to say why. Removed at the top of `start()`.

### Three of my own test bugs, worth recording

The audit's first run failed seven checks. Three of them were the harness, not the site, and each
was a different mistake worth naming:

- **Live cast and director were "missing"** because the stub returned credits from
  `/movie/{id}/credits`. `js/api.js` asks for credits, recommendations and similar via
  `append_to_response` on the *same* `/movie/{id}` call, so the stub was answering a request the
  site never makes and the real one went unanswered.
- **A TMDB 404 rendered as success** because the catch-all stub returned `200` with an empty object
  for any URL. A stub that never fails cannot test the error path, which is most of the point.
- **Empty slots on About** were the three `.field__error` spans and `#contact-status`. Those are
  live regions, which are *supposed* to start empty — that is what makes them live regions. The
  exemption is now principled (`role="alert"`/`role="status"`/`aria-live`) rather than a name list.

### Also checked, and clean

All five pages boot with no uncaught error and no `console.error`. Every `aria-labelledby`,
`aria-controls` and `aria-describedby` resolves to a real id; every `<label for>` has a control.
No duplicate ids. The `<header>`, `<nav>` and `<footer>` blocks are byte-identical across the five
pages — now enforced by a smoke check rather than by my having diffed them once. An unknown
`?id=`, a missing `?id=` and a keyless offline load all still paint.

### What the audit still cannot tell you

jsdom has no layout engine. Every check above is about behaviour, DOM structure and CSS class
coverage. **Nothing here proves how any of this looks at 1440, 1024, 768 or 390 px** — no overflow,
no collisions, no unreadable contrast in practice. That still needs eyes on a browser.

## 15. The layout pass - what a real engine found

The §14 gap was closed with a throwaway headless-Chrome harness (CDP over `ws`) that measures things
jsdom cannot: `documentElement.scrollWidth` against `window.innerWidth`, every element whose box
crosses a viewport edge, the computed colour of each `<h1>`, and the average luminance of the
rendered hero (screenshot decoded back into the page and sampled). It ran 7 page/URL states across
4 widths — 28 combinations — in both themes. Three defects, one of which was a generator bug the
whole audit had missed.

### The details page could not be scrolled sideways

`.detail__layout` is `grid-template-columns: 300px 1fr`. A `1fr` track is `minmax(auto, 1fr)`, so
its floor is the widest child's **min-content** width. The related-movies rail is a horizontal
scroller whose track lays out all eight cards edge to edge — 8 × 210px plus gaps, **1845px** — and
that number became the floor of the whole content column. On a 1440px viewport the column computed
to **1837px**, and `.detail { overflow: hidden }` (stylesheet §12) then clipped it, so the page
never grew a horizontal scrollbar and the stranded half was unreachable. That is the reported "more things on
the left but I cannot scroll to the left", and it hit mobile hardest because the layout collapses to
a single `1fr` track below the tablet breakpoint, with the same floor.

The fix is one line — `.detail__layout > * { min-width: 0 }` — which drops the floor to zero and
lets the rail scroll *inside* itself, which is what a rail is for. Content column 1837px → 845px at
1440; all 28 combinations now report no horizontal overflow. Note this is the opposite of a blanket
`overflow-x: hidden` on `body`: that would have hidden the symptom while leaving the layout broken.

### The hero backdrop was a flat wash, in both themes

Two separate causes stacked:

1. **`tools/gen-posters.mjs` was emitting invalid colours.** `mix()` returns a `"#rrggbb"` string,
   but two call sites passed one of its own outputs straight back in, so it read `.r/.g/.b` off a
   string and produced `"#NaNNaNNaN"`. **206 colours across all 56 generated files** were literally
   invalid, which browsers drop to black. `mix()` now coerces either argument through `hexToRgb`.
   Regenerating produced zero `NaN` tokens.
2. **The scrim was heavy enough to erase the backdrop.** Combined top/right alphas left the image
   at near-black in dark theme and, because `initTheme` follows the OS when nothing is stored, a
   near-white wash in light theme — the state the report described. The scrim was lightened in both
   themes and the backdrop given a small `brightness`/`saturate` lift. A later pass added a
   light-theme-only backdrop filter (`brightness(0.9) contrast(1.12)`, *not* the dark theme's
   brightening) and dropped the white scrim further, because a lift on an already-bright photo is
   exactly what made it blow out. Measured whole-hero luminance is now 46 in dark and 180 in light
   (centre 152), i.e. the film reads as a photograph behind the copy in both, with the light bottom
   edge kept bright for the dark-blue title.

### Titles were inheriting body colour

`h1–h4` set no colour at all. Added `--title` and applied it to `h1–h4` and `.brand__name`, so every
heading including the site name reads blue while red stays the action accent and gold stays reserved
for ratings. The brief's blue is `#0000cd`, used verbatim in both themes (verified `rgb(0, 0, 205)`
on all five pages). It is very low-contrast on the dark background, which is why the *nav* uses a
lighter tint — see §16.

### Still true

The harness is ad-hoc (it needs Chrome, `ws` and the dev server) and lives outside the repo, so it
is not wired into `tests/smoke.mjs`. It proves geometry and colour, not taste — the scrim values in
particular are a judgement call and are the easiest thing here to tune by eye.

## 17. Rendering pass: invisible posters, clipped titles, light hero, header tidy-up

Six reported problems, all reproduced and fixed. Each was measured before and after rather than
judged by eye, because three of them were invisible in a screenshot only at certain sizes.

### Poster art was effectively black

Symptom: on the Movies grid the poster boxes looked empty; the artwork only became visible on the
details page, where it is rendered at 300px instead of 216px.

Measurement: sampling the rendered grid gave poster luminance **14-16** against a page background of
**8**. The images were loading correctly (`complete: true`, `naturalWidth: 500x750`, correct
216x324 box, `object-fit: cover`) on both `http://` and `file://` - so this was never a broken
path. The cause was in `tools/gen-posters.mjs`: `buildPalette()` mixed its base tones from
`{12,11,16}` / `{22,20,30}` / black, and `buildPoster()` then stacked a `fade` gradient reaching
**0.94** black, a vignette at **0.72 x 0.9** opacity, and a 0.5 grain layer over the top. The banner
format survived because it has a `halo` gradient and only a 0.8 vignette - which is exactly why the
same film looked fine on the details page.

Fixed by mixing the base tones much further towards the film accent (`deep` 0.42-0.56, `mid`
0.5-0.7, `glow` 0.34 towards white), cutting the `fade` bottom stop to 0.8 / mid to 0.34, the
vignette to 0.38 x 0.55, and the grain to 0.4. Regenerated: poster luminance **84-110**, far clear
of the background. All 28 posters and 28 banners re-emitted.

### Long titles ran off the canvas

Symptom: "in movie card text is not fit in the fox some are cut".

Two candidate causes were checked and split apart. The card **grid** was innocent -
`.card__body` reports `scrollWidth == clientWidth == 216`, so nothing in the DOM was clipping. The
fault was in the generated artwork: the title lockup sized itself from `line.length * size * 0.58`,
which badly understates a bold serif set in caps. Georgia Bold is 1.00em for M and 1.08em for W, so
`REDEMPTION` is about 7.7em wide, not the ~5.8em the estimate assumed, and long words ran past the
right edge of the 500px canvas.

Replaced the character-count estimate with a real glyph table (`GLYPH_EM`, Georgia Bold advances in
em units, `titleWidth()` and `wrapTitle()` helpers) and a descending size search from 68px that
takes the largest size at which the wrapped title still clears both margins, with a 12px inset
because the table is an approximation and a line flush with the margin reads as clipped anyway.
Verified by re-measuring all 28 emitted SVGs: **0 overflowing**, tightest line ends 13px short of
the margin, sizes span 47-68px and 1-4 lines.

### The light-theme background was too bright

Only the light theme was changed; the dark hero was already right and is untouched.

The filter was not the controlling factor. Dropping `.hero__media img` from `brightness(0.9)` to
`0.4` barely moved the number (157 -> 153) because the **scrim** was doing the brightening: two
white washes at 0.86 and 0.34 sat on top of the photograph. The real fix was thinning those. The
light `.hero__scrim` keeps its bottom ramp (the `h1` sits there and `#0000cd` needs a light
ground) and drops the middle and right-hand layers; the same reasoning was applied to the light
`.detail__scrim` and `.detail__banner img`.

Measured hero luminance, light theme, whole / centre / top-right / bottom-left:

| | before | after |
|---|---|---|
| home hero | 180 / 152 / - / 238 | **118 / 50 / 69 / 221** |
| details banner | 188 / 215 / 192 / - | **149 / 141 / 121 / 131** |

The bottom-left stays light (221) so the `#0000cd` title keeps its contrast.

### Nav links: title blue at rest, red on hover

`--nav-link` now points at the title colour and `--nav-link-hover` at red, per the brief. The dark
theme keeps its `#9cc4ff` tint for the rest state, because `#0000cd` is ~1.8:1 on the near-black
dark background and would be unreadable in the navbar - the titles themselves use `#0000cd` in both
themes as asked. Hover is `#ff4a56` dark / `#c8102e` light. The current page now keeps the same
resting colour as its siblings and is marked by its existing red underline, so hover red stays

### Removed the redundant Browse movies button

It pointed at `movies.html`, exactly where the `Movies` nav link already goes. Deleted from the
shared header on all five pages; the header stays byte-identical across them so the smoke drift
check still passes. The homepage keeps its own distinct CTA ("Browse all movies") in the hero, which

### Save list removed

The watchlist (`cr.watchlist`) is gone end to end: the heart on every card, the "Save to my list"
button in the details sidebar, `initWatchlist` / `paintSaveButtons` / `toggleSave`, the storage key in

### Search: live suggestions

Measured first, and the search was not broken: submitting on `file://` navigates to

## 18. Dark-only, visitor panels removed, and the image-loading fix

### 18.1 Two features cut by request

Three visitor-facing features were removed, each deleted end to end rather than merely hidden:

| Removed | What went with it |
|---|---|
| Light theme | head pre-paint theme script, `data-theme-toggle` button, `applyTheme`/`initTheme`/`keys.theme`, the entire `[data-theme="light"]` CSS block (159 lines), `cr.theme` in both config files |
| Watchlist | card hearts, the details "Save to my list", `initWatchlist`/`paintSaveButtons`/`toggleSave`, `keys.watchlist`, `cr.watchlist`, all `.card__save` CSS including its light and print overrides, and the two pieces of page copy that promised it |
| "Rate it yourself" | `detailUserRate()`, `initUserRate()`, `keys.ratings`, `keys.reviews`, `cr.ratings`, `cr.user-reviews`, the `.user-rate`/`.star-picker`/`.saved-review` CSS, the details print rule, and the About/Reviews copy that described the feature |

**Dark-only was a deletion, not a re-point.** Because no `data-theme` attribute is ever set now,
`:root` *is* the dark palette; rewriting the light block would have left two palettes where one is
reachable. A smoke check asserts there is exactly one theme, so light cannot quietly return. Note
that 17.3's work on light-theme scrims is therefore moot - recorded here for honesty rather than
silently dropped.

Removing `initUserRate()` took `repaintDetail()` and the half-typed-review-text carry-over with it,
so `enrichDetail()` now preserves scroll position directly and nothing else. `.rating-pill` stays:
it also renders TMDB scores and our own verdicts, which were never part of the removed panel.

### 18.2 Navbar colours

Nav links use `--nav-link` (`#9cc4ff`) at rest and `--nav-link-hover` (`#ff4a56`) on hover. `#0000cd`
was specified for the blue, and it *is* the blue everywhere it was asked for - brand mark and every
page title - but at roughly 1.8:1 against the near-black navbar it is unreadable there, so the nav
gets its own token. The current page keeps the resting colour and is marked by the existing red
underline, which keeps "hover turns red" unambiguous.

### 18.3 Why the posters looked broken

Reported as "posters don't render", but they always rendered - `naturalWidth` was 500 on every card.
Three separate faults sat behind the report:

**a. Art too dark to see (fixed in 17.1).** Poster luminance measured 14-16 against a page background
of 8. Not a loading fault at all; the generator was painting near-black art. Now 84-110.

**b. `posterFor` would mint a path from a missing id.** `data.js` interpolated the id straight into a
template literal, so a record without one produced `images/movie-posters/undefined.svg` - a real
string, truthy, and a 404. `adapt()` then trusted it unconditionally:

```js
poster: live ? record.poster : data.posterFor(record)
```

Measured: a live TMDB record with no `poster_path` came out of `adapt()` with `poster: ""`, and a
record with no id came out with `poster: "images/movie-posters/undefined.svg"`.

**c. The fallback handlers had drifted apart.** Nine `<img>` emitters each rolled their own inline
`onerror`. Six substituted the placeholder. One - the nav-search thumbnail - did
`this.removeAttribute('src')`, which leaves a reserved-but-empty frame. The cast photos had **no
handler at all**, so a dead TMDB profile URL stayed broken permanently. `src=""` is a third trap:
Chrome reports `complete: true, naturalWidth: 0` and never fires `error`, so an empty src cannot be
recovered by an `onerror` at all.

So the loading logic was not one thing with one bug. It was nine things with three bugs, which is
why fixing one never made the symptom go away.

### 18.4 One resolver for every image

`resolveImage(live, local, fallback)` picks the first usable candidate, rejecting `""`, `null`,
`undefined` and the literal strings `"undefined"`/`"null"`. Precedence is deliberate: live TMDB art,
then the bundled generated SVG, then the placeholder. The middle step matters - a film we have
written about chains `TMDB -> our SVG -> placeholder`, and because that SVG is art-directed it
recognisably *is* that film, where the generic placeholder would not.

`artworkImg()` builds the tag. All nine call sites now go through it, so Home, Movies, Reviews and
Details cannot drift apart again, and the `onerror` handler exists in exactly one place.

The handler hops once and then gives up:

- next-best URL available -> try it, arm a second handler;
- second failure -> remove the `src`, add `is-image-missing`.

The hop guard is what stops a missing *placeholder* from becoming an infinite reload loop.

**Two bugs found in the fix itself, both worth recording:**

1. `posterLocal` was initially derived from the live record, which has none of our ids, so it was
   always empty and the chain never worked. Fixed to read from `ours`, the bundled record.
2. The first `onerror` string nested `"` inside a double-quoted HTML attribute. That closes the
   attribute early and *silently truncates the handler* - the images then 404 with no error handling
   at all, reproducing the original bug exactly. The DOM showed the damage plainly: the attribute
   parsed as `onerror="this.onerror=null;var n=...this.onerror="` plus a junk attribute named
   `this.onerror`. Rewritten single-quote throughout, with the second hop reassigned as a *function*
   rather than a string so it never re-enters attribute-quoting.

Cast photos get their own handler that swaps the dead `<img>` for the initials circle already used
when TMDB has no headshot - a poster-shaped placeholder in a 40px round frame would look wrong as
